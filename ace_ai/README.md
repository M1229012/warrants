# 艾斯 AI｜Discord 台股問答助理

在 Discord 輸入 `/ask 問題`，Bot 抓取股價、技術面、大量區、權證分點、A～E 事件績效、新聞與族群名冊，整理成**一張圖片**回覆。

- **數字全部由 Python 計算**：重用 repo 根目錄 `K_function_warrant_report_20260530.py` 的函式，以及回測寫進 Google Sheet 的結果。Gemini 只負責文字解讀，而且每一句都會經過事實核對。
- **Bot 對 Google Sheet 只讀不寫**；不影響週報、回測或任何 GitHub Actions。
- **Bot 不會下單**；回答只描述技術結構與條件，不給買賣指令、目標價或上漲機率。

---

## 使用方式

指令分成兩個，互不干擾：

| 指令 | 誰可以用 | 做什麼 |
|---|---|---|
| `/ask` | 所有人 | 個股、族群、權證分點、新聞等一般問答 |
| `/ace` | 只有伺服器管理員 | 本週精選排名、草稿生成與修改、產圖、資料維護 |

這樣草稿編輯不會吃掉一般問題：草稿開著時 `/ace` 的訊息才算改稿，`/ask` 永遠照常回答。`/ace 說明` 可看管理員指令清單。`!ace` 文字指令預設關閉（`DISCORD_AI_PREFIX_COMMAND_ENABLE=1` 才開）。

| 想問的事 | 範例 |
|---|---|
| 型態好不好（K 線＋型態評分卡） | `/ask 2409現在型態好嗎` |
| 持股成本怎麼看 | `/ask 我2409成本30元該怎麼看` |
| 兩檔比較 | `/ask 2344跟2408誰比較好` |
| 只問股價（不呼叫 AI） | `/ask 2330股價多少` |
| 新聞利多利空 | `/ask 2344最近有什麼新聞` |
| 權證分點與高勝率分點 | `/ask 2409權證分點買賣`（預設看近 70 個交易日，和 K 線圖同一區間） |
| 權證淨買超排行 | `/ask 目前權證買超金額最大的是誰` |
| 分點 A～E 事件勝率 | `/ask 永豐金內湖D事件勝率` |
| 分點近期操作 | `/ask 永豐金內湖最近在買什麼` |
| 分點在某檔的部位 | `/ask 永豐金內湖2409部位還在嗎` |
| 分點勝率排行 | `/ask 勝率最高的分點有哪些` |
| 族群型態排行 | `/ask 記憶體族群現在誰形態最好` |
| 族群盤中漲幅 | `/ask 散熱族群盤中誰最強` |
| 族群成分股 | `/ask PCB族群有哪些` |
| 支援哪些族群 | `/ask 有哪些族群` |

**追問**：同一個人在同一個頻道 30 分鐘內可以接著問，不用重打股票。

```text
/ask 幫我分析華邦電
/ask 那它的壓力在哪        ← 自動接華邦電
/ask 跟南亞科比呢          ← 變成華邦電 vs 南亞科
/ask 重新開始              ← 清除上一題
```

回答最上面會用小字標出「※ 延續上一題：華邦電（2344）」，讓使用者知道 Bot 是怎麼理解這題的。

**本週精選**（改用 `/ace 本週精選排名`、`/ace 本週精選 只看D事件 勝率70%以上`；也可以打「本周精選」「本州精選」「每週精選」「每周精選」「精選股票」「精選個股」）只開放給**伺服器管理員**（有「管理員」或「管理伺服器」權限的人）以及 `DISCORD_AI_WEEKLY_PICK_USER_IDS` 裡的使用者，使用說明不會顯示這項功能。候選只看 1～9 開頭的 4 碼普通股，**ETF（0 開頭，例如 0050、00878、00631L）一律排除**。候選必須在 Google Sheet 權證事件資料中、近 60 個交易日曾買超且目前仍有未出清部位；0～60 日只決定資格，不做新鮮度扣分。精選五分點與其他分點使用相同規則，僅在結果以 ⭐ 標示，不加分。

## 回答圖片

| 問題類型 | 圖片內容 |
|---|---|
| 單一個股 | K 線卡（MA5／10／20／60、布林上下軌、價量分布、成交量與均量線、分點買賣標註）＋型態評分卡（分數、五大項、主要得分／失分、均線扣抵、關鍵價位、追蹤分點動向）＋AI 回答 |
| 兩檔比較 | 兩張精簡 K 線（不畫分點標註）＋一張「型態比較」並排表（分數、五大項、型態、均線、最近壓力／支撐、追蹤分點、盤中觀察）＋AI 回答。長度約為單檔版的兩倍，而不是四倍 |
| 權證淨買超排行 | 排行＋第一名的 K 線與評分卡 |
| 族群排行 | 前三名卡片（名次、分數與分級或漲幅、股價、分數條、優勢／留意、AI 解讀）＋第 4～5 名排行表（最多顯示到第 5 名）；不顯示名冊來源與檔數統計，只在有個股缺資料時加一行小字說明 |
| 族群成分股 | 依上市／上櫃分組的股名標籤 |
| 週精選文章 | K 線（分點買賣標註）＋型態評分卡＋文章卡（標題、分段內文、底部免責） |
| 本週精選 | 先顯示單張 Top 10 排名；管理員指定個股生成文字草稿、修改確認後，再產生 K 線＋實際權證分點買賣超點位圖片 |

- **浮水印**：所有回答圖片沿用週報的「股市艾斯／台股DC討論群」，藏青色 `#1D2B44`、透明度 6%、旋轉 18 度。長圖上下各一枚；短圖置中一枚並縮小，避免重疊。一般文字圖卡、族群卡片、本週精選每一頁與 PNG／JPEG 附件均包含浮水印，無須新增環境變數。修改後需重啟或重新部署 Bot，舊訊息圖片不會回溯改動。
- **MA20 就是布林中軌**：數值卡寫成「MA20／中軌」，K 線上不另外畫中軌虛線，關鍵價位表也只列一次。
- **關鍵價位會優先保留附近大量區，但改成精簡顯示**：最大／第二大量區若距現價不遠（預設 12% 內）會保留；股價在量區上方只顯示量區上緣、在量區下方只顯示量區下緣、只有股價落在量區內才同時顯示上下緣。
- **週精選的分點標註**：一個分點一個顏色，K 線上的三角形與編號都用該分點的顏色，下方圖例列出「● 分點名｜編號 1、3、5｜買超 2 筆 賣超 1 筆」，看得出每個點位是誰；標註與「追蹤分點動向」都只顯示最終確認文字實際提到的分點。
- **分點買賣標註**：一般型態問答仍可使用 A～E 事件標註；若問題包含「權證買賣超／買在哪／賣在哪／進出點位」，或管理員確認週精選圖片，改用實際權證流水模式，先以「分點 × 股票 × 日期」聚合同日淨買賣後再畫 ▲買超／▼賣超，降低換倉造成的一買一賣假訊號。
- **圖上不出現資料供應商名稱**（FinMind、富果、Google Sheet、工作表名稱），只寫「日K收盤資料」「盤中即時報價」「追蹤分點統計」；新聞媒體名稱照寫。
- **日期寫法**：扣抵推算寫「明天起／後天起／N 個交易日後」，不寫「第 N 日」。
- PNG 超過附件容量時改 JPEG；股價抓不到時圖內標示缺資料，保留其他分析。

### 分點標註與缺資料處理

一般問答的事件模式與「實際權證流水模式」分開。使用者明確問某股票／分點的權證買賣超點位時，流水模式不要求先形成 A～E 事件，而是直接依當日分點淨買賣畫點。未指定分點時只保留區間內累積淨額較大的少數分點，避免圖面過度擁擠。

**圖片不再顯示任何缺資料、篩選原因或 coverage 註解。** 有資料就畫，沒有就省略該區塊；資料讀取失敗與篩選原因只寫入 Log，避免會員圖片被系統說明污染。

## 型態評分（100 分）

只評技術結構，不含籌碼，不是買賣建議。與本週精選共用同一套規則（`weekly_pick.score_pattern`）。

| 項目 | 權重 | 看什麼 |
|---|---:|---|
| 均線趨勢 | 25 | 均線排列、MA20／MA60 方向與扣抵 |
| 價格位置 | 15 | 相對 MA20、近期漲幅是否過熱 |
| 量區結構 | 25 | 相對兩大量區的位置（漸進計分，接近量區下緣也給部分分數） |
| 下方支撐 | 25 | MA10／MA20／大量區等支撐的距離與品質 |
| 布林 | 10 | 開布林方向與位置（中軌方向已算在 MA20，不重複） |

分級：≥75 結構偏強、≥60 中性偏多、≥45 結構中性、≥30 中性偏弱、其餘結構偏弱。

本週精選綜合分數＝技術面 50＋權證面 50。**技術面不再維護第二套評分**：直接使用一般個股分析同一個 `score_pattern()` 的 100 分型態評分，線性換算為 `型態分 × 0.5`，例如一般型態 94/100，在本週精選固定就是技術 47/50。權證面拆成「本次事件／精確複合事件歷史績效 20＋有效權證部位金額 15＋持倉／操作狀態 15」。勝率優先使用 Sheet 已存在的精確複合事件（例如 A+C）；找不到才退回單事件資料，分點總勝率只作背景資訊，不覆蓋高勝率事件。預設排除 2330（`WEEKLY_PICK_EXCLUDE_CODES`）。

### 管理員週精選工作流

1. `/ask 本週精選排名`：純 Python 排出 Top 10，排名階段不呼叫 Gemini。
2. `/ask 3034 幫我生成週精選文字`：只允許當期 Top 10 候選，AI 依 `weekly_style_examples.txt` 的歷史文風與當期 facts 產生草稿。
3. 接著直接說「權證部分短一點」「大量區再強調」「不要寫某段」：同一 Discord 使用者／頻道 session 持續修改同一份草稿。
4. `/ask 這版確認，生成圖片`：以最後確認文字產圖，版型沿用一般個股 3034 風格；K 線與「追蹤分點動向」都只顯示最後確認文字實際提到的分點，並保留型態評分卡中的「關鍵價位」。不會因其他分點金額較大、勝率較高或屬精選五分點而自動補入。
- **所有排名型圖片**（族群型態排行、漲幅排行、本週精選 Top 10）固定顯示：「※ 排名僅供研究與觀察參考，不代表未來表現，亦非買賣建議。」

上述排名、草稿、修改與確認圖片流程沿用本週精選管理員權限；一般會員不能啟動。

## 盤中與收盤

設定 `FUGLE_API_KEY` 後，平日盤中會在日 K 後面接上一根盤中 K 棒；沒設或抓不到就只用日 K，K 線不會留白。

訊號分三種狀態，AI 不可混用：

| 狀態 | 內容 |
|---|---|
| 收盤確認 | 型態評分、均線／布林訊號、大量區，一律用**最後一根已收盤 K 棒**計算 |
| 盤中暫時 | 盤中和收盤不同的地方另外列出，例如「盤中暫時站上 MA20（前一日收盤為跌破），尚待收盤確認」；評分卡用黃色小框標示，不計入分數 |
| 資料不足 | 欄位缺值時寫「目前無法確認」，不當成沒有訊號 |

- 盤中那根的 MV5／MV20 沿用前一日，**盤中累計量不和日均量比較**，也不判斷量縮量增。
- 盤中成交量單位固定換算（`FUGLE_QUOTE_VOLUME_UNIT`，預設 `lots`＝張）。和近 20 日均量相比超過 30 倍或低於 0.001 倍時標成可疑，不解讀量能。
- 啟動時 Log 會印 `📏 富果成交量單位校正：…`（收盤後比對盤中累計量與日 K 量），依結果確認單位設定。

## AI 回答與事實核對

- **Prompt 依問題組合**：基本規則＋技術面／新聞／型態／排行規則，只放這題用得到的段落；送出前刪掉說明欄位與圖上已有的數值，節省 token。
- **一定先寫【回答】**直接回應問題；型態題最多再加 3 行【觀察重點】。比較題第一句要下結論（「就技術結構來看，X 比 Y 好」，分數差不到 5 分寫「差不多」）。
- **事實核對（`FactSheet`，純 Python，不多花 Gemini）**：逐句檢查下列問題，有問題只刪那一句。
  1. 數字對不上原始資料（大金額可精確換算成萬／億）。
  2. 句子只講一檔股票，卻用了另一檔的數字。
  3. 「月線 31.2 元」這類均線數值寫錯（容許 0.6%，扣抵價也算對）。
  4. 「站上／跌破」和收盤確認的位置不符；句中有「盤中／暫時／目前」才可用盤中位置。
  5. 把使用者問題裡的價格（成本、假設跌到多少）當成現價。

  條件句、否定句、均線彼此交叉、成本與均線比較不核對方向，避免誤刪。刪到剩不到六成才整篇改用系統排版的資料。Log 會寫「事實核對：刪除 N 句｜句子（原因）」。
- **新聞**：鉅亨網個股新聞 API（含內文），AI 分【可能利多】【可能利空／風險】整理，聳動字眼與法人預估不當成事實。

## 多人使用

| 機制 | 預設 |
|---|---|
| 一般問答同時處理 | 3 題（`DISCORD_AI_ANSWER_CONCURRENCY`） |
| 排隊上限 | 20 題（`DISCORD_AI_QUEUE_LIMIT`），滿了回「排隊已滿，請過一兩分鐘再問」 |
| 排隊通知 | 需要排隊時先把回覆圖更新成「前面還有 N 個問題」，輪到時自動換成答案 |
| 相同問題 | 同時有人問同一題只算一次，大家共用結果 |
| 本週精選 | 獨立排隊，一次一個，不卡一般問答 |
| Gemini 同時呼叫 | 2 個（`DISCORD_AI_GEMINI_CONCURRENCY`） |
| 只問股價 | 走輕量流程：不呼叫 AI、K 線不查分點標註 |
| 同一人冷卻 | 8 秒；上一題還沒完成不能再問 |

**追問記憶**只存「股票代號、成本、分點、時間」，不存對話原文；鍵值是伺服器＋頻道＋使用者 ID。30 分鐘沒追問自動忘記，最多 5,000 筆（最舊的先刪），Bot 重啟即清空。排行、分點勝率、族群、打招呼這類問題不會接上一題的股票。

## 族群

## 資料底庫（2026-09-20 起）

| 資料 | 怎麼來 | 成本 |
|---|---|---|
| 全市場日 K | 證交所／櫃買官方「依日期查全市場」，寫入本機 SQLite | 一個交易日 **2 個請求**，不用金鑰、不吃 FinMind 額度 |
| 型態分數 | 背景用同一套 `score_pattern` 逐檔算好存起來 | 純 CPU，沒有 API |
| 族群成分名冊 | 離線掃一次全市場建成 `sector_roster.json` | 平常查詢 **完全不連外** |

- Bot 開機會自動把底庫補到 140 個交易日，之後每個交易日收盤後只補當天。
- 個股查詢、族群排行、全市場排行都直接讀本地，所以第二次之後幾乎都是秒回。
- **建議在 Railway 掛一顆 Volume 到 `/data`**（Service → Settings → Volumes → Mount path 填 `/data`）。沒有掛的話，底庫與名冊會在每次重新部署後重建（約 5～10 分鐘）。「系統狀態」會顯示目前是不是永久保存。

### 族群名冊怎麼維護

概念股、集團股官方沒有公開名單，所以用離線工具掃一次 CMoney 的個股頁反查，一次得到所有族群的完整成員：

```bash
python ace_ai/sector_roster.py build      # 掃全市場，約 10～20 分鐘，產生 sector_roster.json
python ace_ai/sector_roster.py show 記憶體  # 檢查某個族群的成員
python ace_ai/sector_roster.py stats       # 看名冊統計
```

產生的 `sector_roster.json` 跟著程式一起上傳即可；族群成員變動很慢，大約一個月重建一次就夠。管理員也可以在 Discord 說「更新族群名冊」讓 Bot 在背景重建。

大產業分類用 FinMind `TaiwanStockInfo`（富果 `TSE`／`OTC` 名冊備援）；30 個細分族群用證交所／櫃買中心公開產業價值鏈網頁，合併上市、上櫃並依代號去重，網站失敗時用 `fine_sector_seed.json` 快照。

- 「形態／型態／比較好」依型態分數排名；「盤中／漲幅／誰最強」依最新漲跌幅排名。圖上顯示前三名卡片與第 4～5 名；有個股缺資料時只加一行小字說明，不宣稱是全族群前三名。
- 技術排行只比較同一個收盤日期的評分；盤中漲幅排行排除非當日或超過 15 分鐘的報價。
- **排除成交清淡的個股**：近 20 個交易日平均成交金額 5,000 萬元以上、且平均成交量 500 張以上才列入排行（兩個條件都要達到），避免把沒什麼人交易的冷門股排到前面；門檻寫在圖卡副標題。可用 `DISCORD_AI_SECTOR_MIN_AVG_VALUE`、`DISCORD_AI_SECTOR_MIN_AVG_LOTS`、`DISCORD_AI_SECTOR_LIQUIDITY_DAYS` 調整。
- 排名、分數、價格與時間由 Python 輸出，AI 最多呼叫一次補充每檔解讀，且逐檔經過事實核對。
- **簡稱會合併同名族群**：問「散熱」會同時涵蓋散熱零組件與散熱模組（奇鋐在散熱模組），不會因為名稱差一個字就漏掉代表股。
- **族群追問有記憶**：先問「散熱族群誰最強」，再問「那誰型態最好」會接續同一個族群（30 分鐘內）。
- **「現在所有族群誰最強／誰型態最好」**：用名冊 ＋ 本地底庫算出每個族群的中位漲幅／中位型態分數，秒回並附排行圖卡。族群成員少於 5 檔、或算得出數值的比例低於 60% 就不列入，避免用 3 檔代表一個族群；底庫還沒建好時會直接說明原因，不會給看起來像全市場的排行。
- HBM、CPO、AI 伺服器等沒有精確公開分類的題材，會提示未支援，不套用較大的分類。

分類清單、快取與可選變數詳見 [族群功能說明](SECTOR_README.md)。

## 技術細節

### 價量分布

直接呼叫週報 `_calculate_weighted_volume_profile_stats(..., n_bins=40)`（影線各 20%、實體 60%），保留完整 40 格：最大量區紅色、第二大量區橘色、其他淺藍色，透明度與週報一致。缺成交量時顯示「價量分布暫無有效資料」，不推測色帶。

### 布林判讀（`bollinger_analysis.py`）

軌道使用週報 `calculate_indicators` 的 BB_UPPER／BB_MID／BB_LOWER（20 日 ± 2 倍標準差）。以下是本專案採用的門檻，不代表所有工具都用同一套標準。

| 觀察 | 規則 |
|---|---|
| 向上／向下突破 | 前一日收盤在軌內、本日收盤跨越上／下軌；連續在軌外標為持續軌外 |
| 影線穿越 | 高／低價穿越軌道但收盤回到通道內，不當成突破 |
| 重返通道 | 前一日收盤在軌外，本日回到上下軌之間 |
| 壓縮 | 本日帶寬 ≤ 前 60 個有效帶寬的第 20 百分位（不足 60 日為未知） |
| 收窄／擴張 | 帶寬相對 5 個交易日前減少／增加至少 10% |
| 橫盤 | 近 10 日收盤都在軌內、中軌變化 ≤1%、收盤高低差 ≤6%，且帶寬沒有擴張 |
| 沿上軌／沿下軌 | 連續 3 日 %b ≥80% 且中軌上升／%b ≤20% 且中軌下降 |
| 壓縮後突破 | 前 5 個交易日曾壓縮，本日收盤首次跨越上／下軌 |

帶寬＝（上軌－下軌）／中軌 ×100；%b＝（收盤－下軌）／（上軌－下軌）×100。觸軌本身不是買賣訊號，AI 也不可由壓縮自行預測方向。參考：[Bollinger Band Rules](https://www.bollingerbands.com/bollinger-band-rules)。

### 等待圖更新

本週精選、排隊等候時，先送出「計算中／排隊中」圖片，完成後**在同一則訊息替換附件**，不保留舊圖；例外時換成錯誤圖片。等待訊息被手動刪除時才重新發送，私人回覆不會轉成公開訊息。Discord interaction token 有效 15 分鐘，超時或 Bot 重啟時無法保證更新。

## v8：細族群、盤中型態、持久快取與 API 額度保護

### 族群資料與辨識
- 族群問題優先使用 **CMoney 細產業／概念分類**；抓到的名冊存到 Persistent Volume，Bot 啟動後載入記憶體，不會每次問答重新抓目錄。
- 既有細族群與 FinMind 大產業仍保留為備援。
- 輸入採「文字寬鬆、成分精準」：可修正常見錯字與唯一的模糊名稱，但股票成分只能來自實際對應名冊。
- `CPO`：若 CMoney 有直接分類，直接使用；沒有時才明確 fallback 到「光通訊」，不把兩者永久視為同一族群。
- 族群型態／漲幅查詢**不會抓 MoneyDJ 權證資料**。MoneyDJ 只在權證、分點或週精選需要權證流水時使用。

### 盤中與收盤後資料
- 本地 SQLite 保留最近約 **70 個交易日**的 OHLCV 與型態 score snapshot；建議 Railway Persistent Volume 掛在 `/data`。
- Fugle 不做全市場預抓：前 69 日優先讀本地／FinMind，只有「今天這一根」在使用者查詢時才補 Fugle 即時行情。
- 盤中型態分數使用「歷史 + 今日暫時 K」重算，會隨現價改變，並標示盤中暫定；最終仍以收盤確認。
- 13:30 後若 Fugle `isClose` 尚未成立，先標為「盤後暫定」。曾被查詢的股票每至少 15 分鐘可背景重查一次；使用者再次問答時，在預設 120 分鐘查核視窗內也會重新確認。只有 `isClose=True` 才寫成正式收盤日 K。

### 盤中族群
- `/ask 現在所有族群誰最強`：讀 CMoney 盤中族群雷達快取，不掃全市場 Fugle。
- CMoney 雷達在交易時段每約 5 分鐘背景更新一次；會員問答直接讀快取。
- `/ask 某族群誰型態最好`：成分股使用對應精確名冊；歷史資料已有本地 69 日時不重抓 FinMind，只補今天即時行情。族群掃描一次只允許一組進行，避免多人同時把 Fugle 60/min 打滿。
- `/ask 現在哪個族群型態最好`：只使用目前已有足夠 coverage 的 pattern-score cache 做跨族群中位數比較；不為單一問題瞬間掃完整市場。

### API 額度與 Railway Log
每隔 `DISCORD_AI_USAGE_LOG_SECONDS`（預設 300 秒）印出：
- Railway process RAM / CPU / Disk
- 30 分鐘追問 session 數、query queue
- 本地 OHLC / pattern-score cache 筆數與檔案大小
- Fugle 最近 60 秒 / 10 分鐘 calls、errors、暫定收盤待確認數
- FinMind `/v2/user_info` 官方 used / limit（有 Token 時）
- CMoney / MoneyDJFlow / GoogleSheet / Gemini 呼叫次數、錯誤與平均延遲

Fugle Basic 額度保護：
- 背景工作預設最多 `15/min`
- 使用者直接查詢仍優先
- 程式硬上限預設 `55/min`（官方 60/min 前預留安全空間）

### 追問記憶
- 仍依 `guild:channel:user` 隔離，預設 30 分鐘。
- 每筆只存最多 2 檔股票、1 個成本、1 個分點與時間戳，不保存完整對話內容。
- 50 位使用者在 30 分鐘內各有一筆 session 對 RAM 幾乎可忽略；真正需要監控的是同時問答數、外部 API 額度與圖片產生時間。
